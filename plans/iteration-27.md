# Iteration 27 — Seed sharing (specced + implemented 2026-08-06)

> "can we do something similar to slay the spire where we can get a random
> string that acts as the hash so we can replicate the run"

Iteration 9's full-run determinism already means `RunState.map.seed` (one
number) fixes the entire sector — map, escalations, commander draw, every
later shop/event/combat roll. This iteration is purely a presentation
layer on top of that: a short string a player can read aloud, type, or
paste, so two players (or the same player twice) can start from the exact
same sector.

## 27.1 Seed codes (`src/game/seedCode.ts`)

Crockford's Base32: 32 symbols, digits 0-9 then letters with I, L, O, U
dropped (I/L/O look like 1/1/0; U is dropped by the original spec to avoid
accidental words). `seedToCode` encodes a uint32 seed as a fixed 7-character
code; `codeToSeed` decodes a player-typed string back, case-insensitive,
tolerant of whitespace/stray separators, folding O→0 and I/L→1.

**Bug found and fixed before shipping:** 7 base32 digits address up to
32⁷-1 (~34.4 billion) — comfortably past a seed's actual uint32 ceiling
(~4.3 billion, `0xFFFFFFFF`). The first implementation decoded with
`n >>> 0`, which silently wraps an out-of-range code modulo 2³² instead of
rejecting it. Caught by hand-testing in the browser: typing `7GQK2XJ` (a
right-length, right-alphabet, but out-of-range code) silently started the
sector for `3GQK2XJ` instead of reporting an error — exactly the "why did
this happen" failure mode a seed feature can't afford, since the entire
point is reproducing a *specific* sector, not *a* sector. Fixed by
checking the decoded value against `MAX_SEED` (`0xFFFFFFFF`) and returning
`null` if it's exceeded, rather than wrapping. Codes generated by this app
always start with a digit 0-3 (`3ZZZZZZ` is the last valid code), so this
never affects a code copied from the app itself — only a mistyped or
made-up one, which is exactly the case that must fail loudly.

**Considered and rejected: vanity seeds (hash a typed word into a seed,
Slay-the-Spire style).** `daily.ts` already has an FNV-1a string hash that
could serve this. Rejected because it's the wrong shape for *this*
feature: a hash accepts any input and always "succeeds," so a genuinely
mistyped code (transposed characters, a dropped digit) wouldn't be
rejected — it would silently hash into a different, valid-looking sector
with no warning. That reintroduces the exact wrap-around failure mode
above through a different door. Parked in `plans/parking-lot.md` as a
possible *additional* input mode later (accept either a strict code or an
arbitrary phrase, clearly distinguished in the UI) rather than a
replacement for validated codes.

## 27.2 Surfaces

- **Landing screen** (`LandingScreen.tsx`): a "Have a run seed? Start that
  exact sector:" input + Go button, under the New/Continue run buttons.
  Invalid input shows an inline error rather than silently failing or
  guessing. No `maxLength` on the input — `codeToSeed` already does its
  own length/range validation, and truncating a pasted code on the way in
  would turn a valid code into an invalid one before it's ever checked.
- **Settings** (`SettingsScreen.tsx`, both the mobile tab and desktop
  modal): a "Run seed" row showing the current run's code with a Copy
  button — the read-only counterpart to the landing screen's input, for
  sharing a run already in progress.
- **End screen** (`EndScreen.tsx`): the seed + Copy button, shown on both
  victory ("run it back, or hand this sector to someone else") and defeat
  ("want another shot at this exact sector?") — defeat is the moment a
  player most wants to replay the exact fight that beat them, so it's
  surfaced right there rather than requiring a trip through Settings.

**Daily-run suppression, all three surfaces that read a live run's seed**
(Settings, End screen — the landing-screen input is unaffected, it starts
a *new* run): `App.tsx` computes `settingsSeed = state.mode === 'daily' ?
null : state.map.seed` once and passes it through. `daily.ts`'s
`dailySeed(date)` means every player attempting today's daily shares the
same seed — surfacing it mid-attempt (or on the end screen right after)
would let a player look it up and effectively pre-scout the one sector
everyone's supposed to be seeing cold. `SettingsScreen`'s seed row and
`EndScreen`'s seed block both simply don't render when `seed` is `null`.

## Files touched

- `src/game/seedCode.ts` — new: `seedToCode`/`codeToSeed`.
- `src/game/seedCode.test.ts` — new: round-trip, determinism, case-folding,
  ambiguous-character folding, wrong-length/wrong-alphabet rejection, and
  (the regression for the bug above) exact-repro + boundary tests for
  out-of-range codes, plus a 200-seed sweep confirming no code ever wraps
  into a different seed than the one it was encoded from.

  error; `onNewRunFromSeed` prop.
- `src/components/SettingsScreen.tsx` — `SeedRow`; `seed: number | null`
  prop on both `SettingsScreen` and `SettingsOverlay`.
- `src/components/EndScreen.tsx` — seed block + Copy button; `seed: number
  | null` prop.
- `src/App.tsx` — `handleNewRunFromSeed`; `settingsSeed` (daily-null)
  computed once and threaded to Settings and EndScreen.
- `src/styles.css` — `.landing-screen__seed*`, `.settings-row__seed-code`,
  `.end-screen__seed*`.
